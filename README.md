# vexar-autofix

**An MCP security agent that can prove it fixed your code.**

Every AI code agent asks you to trust its output. This one hands you a receipt.

> Submission for the **Nebius × NVIDIA Global AI Hackathon** — Coding and Agentic Engineering track.
> Built with **NVIDIA Nemotron** models served on **Nebius Token Factory**.

---

## The problem

MCP servers are how LLM agents touch the real world: they run shell commands, fetch URLs, read
and write files, and query databases on an agent's behalf. In the last year they have become a
genuinely attractive target, and the tooling around them has not caught up.

Static scanners (including [Vexar-MCP](https://github.com/RANJITHROSAN17/Vexar-MCP), which this
project builds on) find the sinks. What they cannot do is *fix* them — and the obvious next step,
"point an LLM at the file," produces a new problem: you now have a diff generated by something
that will confidently tell you it worked.

This project takes that seriously. The LLM writes the patch; **a deterministic analyzer decides
whether the patch is real.** A finding is only marked fixed when the scanner that found it can no
longer find it, no new finding appeared, and the target's own test suite still passes.

If any of those three fail, the patch is rejected and the failure is fed back to a stronger model.

## Quickstart

```bash
git clone https://github.com/RANJITHROSAN17/vexar-autofix
cd vexar-autofix
pip install -e .

export NEBIUS_API_KEY=...          # https://tokenfactory.nebius.com

# Confirm the key works, find the right endpoint, and check the routed models exist
vexar-autofix --preflight

# Audit and patch, without writing anything
vexar-autofix --target examples/vulnerable_server.py

# Write the verified patch back
vexar-autofix --target examples/vulnerable_server.py --apply
```

No key yet? The whole pipeline runs offline against a scripted mock, which is how CI tests it:

```bash
vexar-autofix --target examples/vulnerable_server.py --provider mock --rehearse-accept
```

## How it works

```
   target file
        │
        ▼
  ┌───────────┐  findings   ┌──────────────┐
  │  scanner  │────────────▶│    triage    │  Nemotron-3 Nano 30B   $0.06/1M
  │ (Vexar-MCP)│            │  exploitable?│  one cheap call per finding
  └───────────┘             └──────┬───────┘
        ▲                          │ confirmed + autofixable
        │                          ▼
        │                   ┌──────────────┐
        │                   │ patch author │  Nemotron-3 Super 120B $0.30/1M
        │                   └──────┬───────┘
        │                          │ anchor edits
        │                          ▼
        │                   ┌──────────────┐  verification failed
        └───────────────────│   VERIFIER   │──────────▶ Nemotron-3 Ultra 550B $1.00/1M
          rule cleared?     │  rescan      │            + the failure reason
          no new findings?  │  + pytest    │
          tests still pass? └──────┬───────┘
                                    │ all three pass
                                    ▼
                            verified patch + receipt
```

The scanner sits on **both sides** of the agent. It is the oracle the model cannot argue with.

### Three properties that make this safe to run on a real repository

**1. Edits are exact anchor replacements, never line numbers or whole-file rewrites.**
A patch either matches the source byte-for-byte or fails loudly. The model cannot silently
reformat, reorder, or delete code it was not asked to touch — the most common way an AI-generated
diff ruins a review.

**2. Your working tree is never modified until a patch has already verified.**
Every attempt runs against a throwaway copy in a temp directory. `--apply` is the only thing that
writes, and it writes a patch the verifier has already approved.

**3. One finding per attempt.**
Each accepted patch is small enough to review, a failure is attributable to a single change, and
partial progress survives a finding the model cannot solve. One giant patch for every finding fails
as a unit and takes the good work down with it.

### Verification also audits the patch, not just the rule count

Clearing a rule is not the same as fixing the code, and a scanner cannot tell the difference —
it matches patterns. On the first live run, the model produced four patches the scanner accepted
and three were wrong:

| Rule | What it wrote | What it actually did |
|---|---|---|
| MCP005 | `subprocess.run(cmd, shell=False)` | Flipped the boolean instead of building an argv list, so subprocess looks for a file literally named after the whole command. Every command with arguments now raises `FileNotFoundError` |
| MCP006 | validated the URL's scheme | Nothing. `http://169.254.169.254/latest/meta-data/` has a valid scheme *and* a valid host |
| MCP007 | `resolved.startswith(BASE_DIR)` | `/app-evil/secret` passes a check against `/app` |

So the verifier gained a third stage: a **deterministic patch audit** that reads only the lines a
patch added and rejects remedies that cannot work — `shell=False` on a string, an SSRF "fix" with
no host allowlist, prefix-based path confinement, a base directory derived from the current working
directory. Rejection is fail-closed and the reason is fed back to the model for the next attempt.

This is another rule-based check rather than another model opinion: it costs nothing, cannot
hallucinate, and encodes the review a security engineer would do anyway.

Deleting a dangerous call outright is *reported* rather than rejected — sometimes it is right,
sometimes it silently drops functionality, and no mechanical check can tell which.

### Verification is line-shift invariant

The first version of the verifier compared findings by `(rule, tool, line)`. A patch that deleted
two lines and added one renumbered everything below it, so a *perfect* fix reported
"1 finding cleared, 6 new findings appeared" and was rejected. Every correct multi-line patch
would have failed.

It now compares **rule-instance counts per tool**, which survives reformatting and reordering, and
requires the targeted rule's count to actually *drop* — moving a sink to a different line is not
remediation. `tests/test_verifier.py::test_line_shift_is_not_a_new_finding` is that bug, pinned.

## How NVIDIA Nemotron and Nebius Token Factory are used

Token Factory's OpenAI-compatible endpoint (`https://api.tokenfactory.nebius.com/v1`) is the only
inference provider in this project. Three Nemotron models, each with a distinct job:

| Role | Model | When it runs | Why this tier |
|---|---|---|---|
| **Triage** | `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B` | Once per finding, every scan | Classification, not reasoning. Runs on every finding, so it must be cheap. |
| **Patch** | `nvidia/nemotron-3-super-120b-a12b` | Once per queue entry | Real code understanding, at a price where trying is affordable. |
| **Escalate** | `nvidia/Nemotron-3-Ultra-550b-a55b` | Only after a *failed verification* | It gets the failure reason and the rejected patch — actual evidence to reason about. |

**The routing signal is the unusual part.** Tiered-routing demos usually route on *request
difficulty*, which cannot be measured before answering. This routes on **verified failure** — a
signal that is only available because a deterministic checker is in the loop. The expensive model
is never consulted on a guess.

Client is stdlib `urllib`, not the OpenAI SDK: the scanner underneath is dependency-free, and the
agent should not be the thing that changes that. Set `AUTOFIX_MODEL_TRIAGE` / `_PATCH` / `_ESCALATE`
to override any tier without touching code.

## What it fixes — and what it deliberately refuses

| Rule | Meaning | Autofixed |
|---|---|---|
| `MCP005` | `shell=True`, `os.system`, `eval` on tool input | ✅ argv form |
| `MCP006` | SSRF sink with no scheme/host allowlist | ✅ allowlist guard |
| `MCP007` | Filesystem path from tool input, no base-dir confinement | ✅ `resolve()` + containment |
| `MCP010` | Outbound HTTP without an explicit timeout | ✅ explicit timeout |
| everything else | contract, schema, naming, token budget | ❌ reported, left to a human |

The refusal list is the more important one. `MCP001` (a tool description is too short) has no
mechanical fix, and a model guessing at the author's intent produces a diff that looks plausible
and is wrong. **A confidently wrong fix is worse than a known finding**, so the agent says so and
moves on. The report has a `refused` section for exactly this.

## Measuring it

Claims about an AI agent are cheap. This repo measures instead:

```bash
python eval/run_eval.py             # real models
python eval/run_eval.py --provider mock   # offline rehearsal
```

Each fixture declares the **exact** rule set it contains — the fixtures are hand-written, so the
denominator is known rather than estimated. The eval reports findings, queued, fixed, refused, and
regressions per fixture, and exits non-zero on **any** regression: if a patch ever trades one
finding for another, CI goes red.

```
fixture                          found  queued  fixed  refused  regress  score
------------------------------------------------------------------------------
vulnerable_server.py                 9       5      1        7        0  4 -> 34
helper_delegation_server.py          3       3      0        0        0  -
clean_server.py                      0       0      0        0        0  -
```

> The run above is the **offline rehearsal** (`--provider mock`) — no model was called, so the
> edits are scripted and the numbers are not a quality result. Run it with a key to get the real
> table; that is the number that means something.

The `fixed` count being *lower* than `queued` is not a failure to hide. It is the agent correctly
declining work it could not verify.

## Tests

```bash
pip install -e ".[dev]"
pytest            # 41 tests, offline, no key required
ruff check . && mypy src --strict
```

Every test runs without a network or an API key. That is deliberate: the verifier is the component
whose correctness decides whether a patch is kept, so it is tested against the cases that would
silently corrupt a repository — ambiguous anchors, line shifts, regressions, zero-progress patches
— rather than against a recording of what a model happened to say. A test that asserts model output
goes red when the model is upgraded and teaches nobody anything.

## Limitations

- **Single file at a time.** Cross-file data flow is out of scope.
- **Four rules.** The rest are reported, not fixed.
- **No semantic equivalence proof.** The verifier proves the finding is gone and the tests pass; it
  does not prove the patch preserves every behaviour the tests miss. Read the diff.
- **Triage can be wrong.** A "mitigated" verdict on a real vulnerability skips the fix. The
  scanner's findings are always in the report, so a skipped finding is visible rather than silent.
