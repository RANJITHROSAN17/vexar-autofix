vexar-autofix

An MCP security agent that can prove it fixed your code.
The LLM writes the patch. A deterministic scanner decides whether the patch is real — the finding's instance count must drop, no new finding may appear, and the target's tests must still pass. Anything else is rejected, and the reason goes to a stronger model.

01The receipt

Real runs against three fixtures, produced by python eval/run_eval.py with NVIDIA Nemotron on Nebius Token Factory.

02Why the verifier exists

The first live run accepted four patches. Three were wrong, and the scanner accepted all of them — because it matches patterns, not intentions. A verifier that reports “finding cleared, tests green” while handing back a broken tool is worse than no verifier: it manufactures confidence.

The fix: a third deterministic stage reads only the lines a patch added — never the existing file, so pre-existing code cannot trigger a rejection — and rejects remedies that cannot work. It cannot hallucinate, it costs nothing, and it encodes the review a security engineer would do anyway.

03How it works

scan
Vexar-MCP
finds the sinks
triage
Nemotron-3 Nano
exploitable, or already guarded?
patch
Nemotron-3 Super
smallest remedy, as an anchor edit
verify
rescan + pytest
count dropped? nothing new?
escalate
Nemotron-3 Ultra
only after a verified failure

The routing signal is the unusual part. Tiered demos usually route on request difficulty, which cannot be measured before answering. This routes on verified failure — a signal that only exists because a deterministic checker is in the loop.

04What it refuses

Seven of the nine findings in the vulnerable fixture are deliberately left alone. A description that is too short has no mechanical fix, and a model guessing at the author's intent produces a diff that looks plausible and is wrong. A confidently wrong fix is worse than a known finding. The report has a refused bucket so a skipped finding is never invisible.
